mainline_framework_fit: sys/base have no single mainline equivalent; they are a Hi3516-style MPP 'SYS+VB' layer. Mapping: (1) VB pool + per-channel waitq/workq/doneq (base_ctx.h:230-239, base_context.c:649-805) corresponds to videobuf2 queues in V4L2 (vb2 with V4L2_MEMORY_MMAP/DMABUF) and to GEM/dma-buf framebuffers in DRM; the cross-module 'common pool' corresponds to dma-buf heaps: mainline cma_heap registers the default CMA area and every DT reserved-memory node with 'shared-dma-pool'+'reusable' as /dev/dma_heap/<name> (drivers/dma-buf/heaps/cma_heap.c:397-421; kernel/dma/contiguous.c:507-589). (2) The bind graph (sys_context.c:164-317) corresponds to media-controller links between V4L2 subdevs; kernel-internal frame forwarding in vb_done_handler would become userspace dma-buf fd passing (or an in-kernel media pipeline). (3) sys cache ops correspond to dma_buf_begin/end_cpu_access / vb2's dma-contig sync; userspace never needs physical addresses. (4) vip_sys.c corresponds to a syscon/simple-mfd node for 0x0A0C8000 plus a reset-simple (or syscon-reset) instance over VIP_SYS_VIP_RESETS and clk gates over VIP_CLK_LP/CLK_CTRL0; mainline clk-cv1800.c already models the VIP clock muxes/dividers in the main clock controller (drivers/clk/sophgo/clk-cv1800.c:626-647) but not the VIP_SYS-local registers, and cv18xx-reset.h has only RST_VIPSYS/RST_VIP_CAM0.
