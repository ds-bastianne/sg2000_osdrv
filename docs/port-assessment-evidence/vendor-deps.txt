Phase-1 reader report: vendor-deps (generated 2026-10-06; evidence as file:line in the named repository; see docs/sg2000-kernel-port-plan.md)

scope: Inventory of what the Sophgo/CVITEK osdrv interdrv/v2 (CV181X/SG2000) modules need from the vendor Linux 5.10.4 tree (/home/user/sg2000_linux_5.10) that mainline Linux 7.3-rc6 (/home/user/mainline_linux) lacks, with a mapping to mainline equivalents. Covers: ION (incl. cvitek heap), efuse, sysdma, TEE include path, clocks, resets, pinctrl, RISC-V non-coherent DMA path, vendor fbdev/media Kconfig stubs, and vendor patches to generic subsystems. No kernel was built.
findings:
  -
    topic: ION heap definition (DT, carveout vs CMA)
    finding: The vendor ION platform driver matches compatible "cvitek,cvitek-ion" and turns each child node into a heap by child compatible: "cvitek,carveout_vpp" (CARVEOUT, name vpp), "cvitek,cma_vpp" (DMA/CMA, vpp), "cvitek,carveout_npu" (CARVEOUT, npu), "cvitek,carveout" (CARVEOUT, carveout), "civtek,cma" [sic] (DMA, cma), "cvitek,sys_contig". Each child becomes a platform device and CARVEOUT/CHUNK/DMA heaps get base/size through of_reserved_mem_device_init, i.e. a memory-region phandle to a reserved-memory node whose compatible is "vpp-region", "npu-region" or "ion-region" (RESERVEDMEM_OF_DECLARE). osdrv only ever allocates from ION_HEAP_TYPE_CARVEOUT (3 occurrences, all in sys.c/ldc_test.c) - so for osdrv the heap in use is a carveout backed by an "ion-region"/"cvitek,carveout" reserved block, not CMA.
    evidence: /home/user/sg2000_linux_5.10/drivers/staging/android/ion/cvitek/cvitek_ion.c:60-73 (heap table), :78-93 (compatible match), :107-117 (of_reserved_mem_device_init for CARVEOUT/CHUNK/DMA), :149-162 (child -> of_platform_device_create), :507 ("cvitek,cvitek-ion"), :532-566 (rmem_ion_setup, RESERVEDMEM_OF_DECLARE vpp-region/npu-region/ion-region); osdrv: interdrv/v2/sys/common/sys.c:57,126 (ION_HEAP_TYPE_CARVEOUT); grep count ION_HEAP_TYPE_* in interdrv/v2 = 3, all CARVEOUT. Kconfig: ion/Kconfig:47-50 ION_CVITEK depends on ARCH_CVITEK && ION, select ION_OF.
    confidence: verified
    implication_for_port: Mainline has no ION and no carveout dma-heap (drivers/dma-buf/heaps contains only cma_heap.c and system_heap.c). The natural replacement is a DT reserved-memory node with compatible "shared-dma-pool" + "reusable" (CMA) which cma_heap.c:397-416 exposes as a named dma-heap per CMA area (dma_contiguous_get_area_by_idx), or a plain CMA/dma_alloc_coherent pool owned by the sys module. Carveout semantics (fixed physical base, no page-struct churn) can be approximated with a large CMA pool; anything that hard-codes physical addresses in user space would break.

    topic: ION alloc/free semantics: fd vs nofd
    finding: cvi_ion_alloc(type,len,mmap_cache) queries heaps via ion_query_heaps (under force_uaccess_begin on riscv), picks the first heap of the requested type, sets flags = ION_FLAG_CACHED iff mmap_cache, and returns a dma-buf FD (ion_alloc). cvi_ion_alloc_nofd returns a bare struct ion_buffer* (ion_alloc_nofd -> _ion_alloc) with no dma-buf. cvi_ion_free(pid,fd) is literally ksys_close(fd); cvi_ion_free_nofd destroys the buffer. osdrv sys.c wraps both: the nofd path reads vendor-only fields ionbuf->paddr/vaddr/name and uses ion_buf_begin_cpu_access to get a kernel vmap; the fd path uses dma_buf_get + dma_buf_begin_cpu_access(DMA_TO_DEVICE) and still reads ionbuf->paddr/vaddr via dmabuf->priv. sys.c is the single ION choke point: all other modules call sys_ion_alloc/sys_ion_alloc_nofd/sys_ion_free* (vb.c, vi, vo, vpss, rgn, ive, fast_image, vcodec vdi.c, jpeg jdi.c).
    evidence: /home/user/sg2000_linux_5.10/drivers/staging/android/ion/cvitek/cvitek_ion_alloc.c:22-75 (_cvi_ion_alloc), :78-90 (nofd), :92-104 (fd), :106-116 (free/free_nofd); ion.c:497-505 (ion_alloc_nofd/ion_free_nofd), :986-990 (ion_free = ksys_close), ion.h:80-83 (#ifdef CONFIG_ION_CVITEK paddr,name in struct ion_buffer); osdrv sys.c:48-114 (_sys_ion_alloc_nofd), :116-194 (_sys_ion_alloc), :298-338 (exports sys_ion_alloc/_nofd/free/_nofd); users: cvi_vc_drv/vcodec/vdi/linux/vdi.c:1886,1973; cvi_vc_drv/jpeg/jdi/linux/jdi.c:1065,1146; grep -l sys_ion_|cvi_ion_ lists 16 files.
    confidence: verified
    implication_for_port: Replace the ION backend inside sys.c only: nofd -> dma_alloc_attrs/CMA (paddr via dma_to_phys or a reserved pool allocator), fd -> dma-heap or dma_buf_export of the same allocation. Mainline dma-buf symbols are exported in the "DMA_BUF" namespace (dma_buf_export/fd/get/begin_cpu_access/vmap at drivers/dma-buf/dma-buf.c:779,804,855,1558,1683), so sys.ko needs MODULE_IMPORT_NS("DMA_BUF"). The ionbuf->paddr/vaddr/name dependence must be replaced with sys-side bookkeeping (already partly present as struct mem_mapping).

    topic: ION cache-attribute handling
    finding: Cache attribute is a per-buffer flag: user mmap gets pgprot_writecombine when !ION_FLAG_CACHED; kernel map uses PAGE_KERNEL (cached) vs pgprot_writecombine(PAGE_KERNEL) via vmap, or memremap(MEMREMAP_WB) vs ioremap for the carveout path. Explicit cache maintenance is exposed by vendor custom ioctls ION_IOC_CVITEK_FLUSH_PHY_RANGE / INVALIDATE_PHY_RANGE which call arch_sync_dma_for_device(paddr,...) directly; the VA-based FLUSH_RANGE variant is compiled out on riscv (#ifndef __riscv). osdrv sys.c additionally exposes its own cache ioctl and sys_cache_invalidate/flush that call arch_sync_dma_for_device on a physical address.
    evidence: ion.c:313-314 (mmap writecombine), ion_heap.c:38-41,58-61,148-151; cvitek_ion.c:286-289 (#ifndef __riscv), :357-381 (PHY_RANGE ioctls -> arch_sync_dma_for_device); osdrv sys.c:376-410 (sys_cache_invalidate/flush and ioctl -> arch_sync_dma_for_device).
    confidence: verified
    implication_for_port: On mainline, uncached/writecombine user mappings work via pgprot_writecombine using Svpbmt/T-Head PBMT page bits (arch/riscv/include/asm/pgtable.h:738-744, pgtable-64.h:139-141 _PAGE_NOCACHE_THEAD, ALT_THEAD_PMA at :257), so the attribute model carries over. The physical-address cache ioctls must be re-implemented with dma_sync_single_for_device/for_cpu on a device that has dma-noncoherent ops (see RISC-V finding) because arch_sync_dma_for_device is not exported in mainline.

    topic: RISC-V non-coherent DMA path (vendor arch code vs mainline)
    finding: Vendor: arch/riscv/mm/dma-mapping.c implements arch_sync_dma_for_device/for_cpu with T-Head dcache.cpa (clean) / dcache.cipa (clean+inv) emitted as .long opcodes, gated on mvendorid 0x5b7, and EXPORTs both symbols GPL so osdrv modules call them directly on physical addresses.
