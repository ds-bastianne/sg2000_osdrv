strategy_name: C - Staged hybrid: compile-first measurement, camera lift-and-shift with vendor uAPI/middleware, display as new DRM/KMS driver (ugly-then-clean), optional V4L2 wrapping of VI
one_paragraph_summary: Answer the feasibility question in the cheapest defensible order. Stage 0 (3-6 eng-weeks, not api-delta's 8-15) compiles only the display+camera chain (sys, base, cif, snsr_i2c, vi, vpss, vo, fb, rgn; ~78k LOC) against 7.3 with -Werror off, ION stubbed and a temporary strncpy compat header, to measure real breakage; the 8-15 figure is inflated by codec (cvi_vc_drv 149k LOC in tree / 55.7k compiled), PWM/RTC/WDT/SARADC (droppable), and the ION shim (design work that belongs to Stage 1). Stage 1 (16-29 incremental) forward-ports the camera chain keeping the vendor ioctl ABI and CVITEK MPI middleware: ION replaced inside sys.c by a CMA-backed dma-buf exporter following the Armbian TPU recipe, cache ops via dma_sync_single_* on a dma-noncoherent device, VIP_SYS owned by base.ko through a DT reg, DT nodes taken from the real SDK DTS (now available), clocks renumbered to sophgo,cv1800.h, CSI PHY resets as raw indices 70-73. This gives a camera on 7.x and validates clocks/resets/DT/cache model with zero 3A work. Stage 2 (12-24) does display as a new DRM/KMS driver (DISP CRTC + primary plane, DSI host with SW ECC/CRC, D-PHY as PHY driver, drm_fbdev_dma) reusing scaler.c 2249-4300 + dsi_phy.c verbatim for first picture (gate at 4-8 weeks), with a concrete split of the SC_TOP block and the shared 'sc' IRQ (syscon regmap for CFG1/INTR bits, IRQF_SHARED with per-driver bit ownership, VPSS online-disp path dropped). Stage 3 (31-58, optional) wraps VI in V4L2 capture/META nodes using vendor structs toward libcamera; it is not needed to answer the feasibility question. Verdict: display feasible (medium confidence), camera feasible as vendor-ABI port (medium), native V4L2/libcamera camera feasible only as a long program (low confidence on image quality); mandatory Stages 0-2 total 31-59 eng-weeks.

userspace_impact: Stage 1 (camera): the CVITEK MPI middleware (libsys/libvb/libvi/libisp/libsns/libvpss, closed, not in the repos) is retained and must keep working against the unchanged /dev/cvi-sys, /dev/cvi-base, /dev/cvi-mipi-rx, /dev/cvi-vi, /dev/cvi-vpss ioctl ABIs (sys-base kernel_interface; vi-isp kernel_interface 53+38 sub-ids; cif-snsr 17 ioctls; vpss 49 ioctls). Three userspace-visible changes are unavoidable: (1) memory comes from a CMA reserved-memory pool instead of the ION carveout - SYS_ION_ALLOC keeps returning paddr + dma-buf fd, but the middleware's direct /dev/ion use for the ISP working pool (ION_IOC_ALLOC + CVITEK flush/invalidate-by-paddr) needs either the /dev/ion compat device in WS2 or a rebuilt libsys on /dev/dma_heap; (2) SYS_CACHE_INVLD semantics change from clean+invalidate to invalidate (must be validated); (3) if the middleware maps tuning buffers via /dev/mem (unverified), Stage 1 needs STRICT_DEVMEM=n or the WS5 mmap-offset rework. ISP tuning files, sensor libraries and 3A are unchanged; vendor RT-thread auto-boost disappears (SCHED_CVITEK) so latency must be re-measured. Panel init: moves from userspace /dev/cvi-mipi-tx ioctls (lane map, timing, DCS packets; vo_mipi_tx.c:163-273) into DRM panel drivers selected by DT - libvo, mipi_tx samples and VO_SDK_* ioctls stop working entirely (vo-mipitx-fb userspace_contract: 'a DRM port breaks all of this'); a compat shim is explicitly not recommended. /dev/fb0 users keep working through drm_fbdev_dma but with XRGB8888 instead of the vendor default ARGB4444 and without the 8-bit LUT mode. VO RGN overlays and cvifb's GOP window become DRM overlay planes (WS11). VPSS->VO kernel-internal binding (SYS_SET_BINDCFG to VO) is replaced by a userspace loop that exports VB blocks as dma-buf fds and page-flips via DRM PRIME (WS12 sample). Stage 3 (optional): camera userspace moves to libcamera (new pipeline handler + IPA); the vendor 3A is either wrapped (licence permitting) or re-implemented; vendor sensor libraries are replaced by drivers/media/i2c subdevs (gc2053/gc2083/gc4653/sc*/os04a10 need new drivers).
maintenance_outlook: Camera chain (Stage 1) stays out-of-tree with the vendor ABI indefinitely: between 5.10 and 7.3 (about 30 releases) the inventory counted 44 breakage classes incl. 3 hard ones (ION, arch_sync_dma export, strncpy removal), so expect 0.5-2 engineer-weeks per major kernel release to re-fix API churn for sys/base/cif/snsr_i2c/vi/vpss (estimate, assumes compat headers isolate most churn and the Armbian branch is tracked rather than every rc). The Sophgo osdrv bm1688 branch shows the vendor fixing the same class of 6.x breakages, which can be mined each cycle (ecosystem Q3). Vendor fixes on sg200x-dev (weekly releases) must be merged manually and re-ported - the local snapshot already lags two years. Display (Stage 2): once the DRM driver, PHY driver and the vip-sys/sc-top syscon bindings are upstreamed (+3-6 wk, calendar months), maintenance falls to normal in-tree churn handled by subsystem-wide refactors; until then it is also out-of-tree but tracks the comparatively stable DRM atomic API. The hybrid split itself carries a maintenance smell: the SC_TOP regmap and IRQF_SHARED patch inside the ported vpss are throwaway if Stage 3 ever replaces vpss with a V4L2 driver. Ecosystem position: no upstream effort exists (wiki 2026-09-02: DRM/Media 'Not Started'); Armbian 7.2/7.3 is the natural home for the patch set and BadgeOS a downstream consumer for the DRM driver, so community maintenance help is plausible for display, unlikely for the vendor-ABI camera modules.
where_this_strategy_is_weak: Versus pure A (lift-and-shift everything including vo/mipi_tx/fb): A reaches a vendor-compatible display in 3-6 (vpss agent) to 6-12 (vo agent) eng-weeks once base/sys/vpss are ported, keeps libvo and the mipi_tx panel-init flow working, and avoids the SC_TOP/IRQ split entirely; C spends 12-24 eng-weeks on display, breaks the vendor VO userspace, and introduces two owners of SC_TOP/IRQ. If the only goal is 'run the vendor SDK on a modern kernel', A is cheaper by roughly 8-15 eng-weeks and lower risk. Versus pure B (native V4L2 + DRM everywhere): C's camera remains a vendor-ABI, closed-3A, physical-address stack that is never upstreamable and must be re-fixed every release; B produces an upstreamable, libcamera-based platform - but at 50-90+ eng-weeks with low confidence on image quality and no TRM coverage for the ISP, so B cannot give a cheap answer. C-specific weaknesses: (1) Stage 0's compile-only gate measures the cheapest kind of breakage (API churn, bounded and mechanical) while the real risk (ION/middleware/cache semantics) only surfaces at G0.5/G1, so G0 is a weaker gate than it looks; (2) the 'ugly-then-clean' DRM path risks stalling at ugly; (3) the hybrid split forces non-upstreamable patches into vpss (regmap SC_TOP, masked IRQ) that are discarded if Stage 3 happens, and Stage 3 itself repeats cif/vpss plumbing (cif-snsr option C: 'double work'); (4) total cost to a defensible answer is 25-43 eng-weeks (G1 + G2), not a few weeks, and to a maintainable result 31-59 - the 'cheapest path' claim holds relative to B, not in absolute terms; (5) several load-bearing facts remain unverified (middleware /dev/mem use, W1C status of INTR_STATUS, 0x03002840 bit 1, pure-MIPI needing no fmux writes, no in-flight upstream series) and the plan's gates are where they get resolved, not before.
