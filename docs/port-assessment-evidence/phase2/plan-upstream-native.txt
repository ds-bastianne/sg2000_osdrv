strategy_name: Strategy B - Upstream-native rewrite: DRM/KMS display + V4L2 media-controller camera + libcamera IPA (display first, camera staged raw -> ISP)
one_paragraph_summary: Replace the osdrv misc/ioctl drivers with new mainline-style drivers: (1) a VIP_SYS syscon/reset/clock-gate provider and an sg2000-vip.dtsi with YAML bindings; (2) a DRM/KMS driver (CRTC = DISP timing generator + DRAM fetch, primary plane, GOP overlay planes, CVITEK DSI host with mipi_dsi_host_ops.transfer, D-PHY TX as drivers/phy, drm_gem_dma + drm_fbdev_dma for /dev/fb0, panels/bridges from mainline incl. LT8912B/LT9611); (3) a V4L2 camera stack (CSI-2 RX subdev + D-PHY RX phy, VI raw-capture then full ISP driver with v4l2-isp.h params/stats, VPSS as m2m scaler first and resizer subdev later, sensors from drivers/media/i2c); (4) a libcamera pipeline handler + IPA with newly written AE/AWB/AF. Order is display first because DISP/OSD/MIPI-TX are documented in the public TRM (ecosystem Q4: vdp.rst:288,292; mipi_tx.rst:147,159), the register HAL is already isolated (vo-mipitx-fb mainline_framework_fit: scaler.c:2249-4300 + dsi_phy.c), Sophgo's own 6.12 CV186x DRM driver is a structural template (ecosystem Q3: drivers/gpu/drm/cvitek, 5.3k LOC; spot-check cvitek_dsi.c:1069-1072 mipi_dsi_host_ops, cvitek_mipipll_cfg.c:8 _cal_pll_reg same as osdrv dsi_phy.c:233-266), and external testers exist (BadgeOS wants DSI->LT8912B). Camera is staged: CSI-RX + VI raw capture (TRM-documented, usable with libcamera 'simple' + softisp) is a go/no-go gate before the ISP driver, which is the largest, least-documented (ISP absent from TRM; only GPL osdrv headers), and quality-riskiest item because all vendor 3A/tuning is closed userspace (vi-isp key_findings: AE/AWB/AF ioctls unhandled, vi.c:5004-5460). Total 75-150 engineer-weeks for everything; display MVP alone 12-24; display MVP + raw camera 26-46; ISP-processed camera with new 3A adds 45-85 more. Vendor MPI middleware is not retained at all.

Image quality parity with the vendor SDK should NOT be assumed.
  overall: Strategy B is the only path that yields upstreamable, long-lived drivers and it is clearly feasible for display. For camera it is feasible but is the slowest route to a usable picture and carries the largest estimate spread (ISP 35-65 eng-weeks across kernel+IPA) plus a licensing dependency: ISP/VPSS register knowledge exists only in osdrv headers that carry 'Copyright (C) Cvitek ... Recommend: commit to display now; commit to CSI-RX + raw capture; make the ISP/3A stage a separate decision at checkpoint G3 after Legal/Privacy/Compliance confirms the licence basis for header-derived in-kernel code and after a quality target is agreed. Total 75-150 engineer-weeks; 2-3 engineers; 12-20 months calendar to an ISP-processed camera, upstream acceptance adding 6-18 months of (overlapping) review calendar (calendar figures are assumptions, not measurements).

scope_out_and_why:
  - Vendor CVITEK MPI middleware compatibility (libsys/libvpss/libvo/libvi/libisp/libsns, /dev/cvi-*, /dev/ion, VB pools, physical-address ioctls): fundamentally incompatible with DRM/V4L2 buffer and device models (vo-mipitx-fb userspace_contract: 'A DRM port breaks all of this'; vpss userspace_contract: 'a shim is impractical'); a compat shim would be a separate non-upstreamable project
  - Forward-porting cvifb.c as an fbdev driver: deprecated path, /dev/fb0 provided by drm_fbdev_dma instead (vo-mipitx-fb api_breakages fbdev 'hard'; mainline-infra Display fbdev policy)
  - I80/HW-MCU (8080) LCD interface: vendor implementation incomplete (vo.c:737-900 mmap commented out, vo_sdk_layer.c:617-651 #if 0) and no clean DRM model beyond DBI; defer indefinitely
  - disp_from_sc online path (SC_D feeds DISP without DRAM): no DRM analogue (scaler.c:4607-4622); default is DRAM-fed (vpss_core.c:1643)
  - DWA rotation of VO frames and RGN handle bookkeeping: rotation becomes a separate m2m (dw100-style) item if ever needed; OSD is DRM overlay planes
  - Sub-LVDS / HiSPi / BT-demux camera inputs: no V4L2 media-bus model (cif-snsr key_findings); only MIPI CSI-2 (and later plain BT656/parallel) in scope
  - snsr_i2c frame-synchronous I2C relay: unnecessary in the V4L2 model (sensor subdevs + libcamera DelayedControls) (cif-snsr mainline_framework_fit)
  - FreeRTOS fast-boot camera (fast_image/rtos_cmdqu) and remoteproc/hwspinlock for C906L: optional coupling only (vi-isp key_findings), no product requirement established
  - Video codec (CODA980/WAVE420L/JPEG), TPU, IVE: separate workstreams; codec has no mainline driver for these cores (codec-others; mainline-infra Codec) and TPU is already ported in Armbian patch 0064. Consequence: this strategy delivers NO hardware H.264/H.265 encode
  - Reusing vendor ISP tuning files or 3A binaries: closed, licence unknown, and tied to the vendor uAPI; libcamera IPA must be new (ecosystem Q3 libcamera; vi-isp userspace_contract)
  - Image-quality parity with the vendor SDK as an acceptance criterion: not achievable without vendor tuning; a measurable but lower target is defined at G4 instead

userspace_impact: All CVITEK MPI middleware stops working and is not replaced by a shim: /dev/cvi-vo, /dev/cvi-mipi-tx, /dev/fb0 (cvifb), /dev/cvi-vpss, /dev/cvi-vi, /dev/cvi-mipi-rx, /dev/ion and the VB-pool/physical-address ABI disappear (vo-mipitx-fb userspace_contract; vpss userspace_contract; vi-isp userspace_contract). Display: applications use DRM/KMS (Weston, kmscube, SDL/GBM); /dev/fb0 is provided by drm_fbdev_dma with XRGB8888 (vendor default 16bpp ARGB4444 and 8-bit LUT modes are gone - vo-mipitx-fb open_questions); panel init moves from userspace DCS ioctls into DT + drivers/gpu/drm/panel/* or bridge drivers (LT8912B/LT9611), so each panel needs a mainline panel driver or a new one; VO overlays (RGN) become DRM overlay planes; VBAT/reboot DCS-off becomes panel/bridge shutdown. Camera: sensor drivers move into the kernel (drivers/media/i2c) - the vendor libsns_*.so sensor libraries and snsr_i2c relay are obsolete; libcamera becomes the camera API (cam/qcam, GStreamer libcamerasrc, PipeWire); 3A/tuning is a new libcamera IPA with its own YAML tuning files - vendor ISP tuning binaries (isp/isp_tuning projects) are not reusable; buffers come from dma-buf heaps/vb2 and are passed as fds (VIDIOC_QBUF DMABUF, DRM PRIME) - no more /dev/mem or physical addresses (STRICT_DEVMEM stays on). VPSS: scaling/CSC via V4L2 m2m (v4l2convert) or libcamera streams; GOP per-scaler overlays, privacy mask, border and encoder slice-buffer handshake are dropped. Codec/TPU/IVE: not part of this strategy - no hardware H.264/H.265/JPEG encode on mainline (CODA980/WAVE420L unsupported); TPU available separately via the Armbian patch 0064 driver with libcviruntime. Boot: the vendor fsbl/U-Boot boot-logo 'smooth' handoff is not honoured; the DRM driver resets and re-initialises the display. Existing product applications written against cvi_mpi/sample_vio must be rewritten (WS11 migration guide).
maintenance_outlook: Best long-term outlook of the three strategies once merged: in-tree drivers are updated by subsystem maintainers for tree-wide API changes (the 12+ breakage classes seen between 5.10 and 7.3 - api-delta/vo-mipitx-fb key_findings - would never have to be chased), bindings are stable, panels/bridges/sensors come from mainline, and libcamera carries the IPA. Until merge (realistically 6-18 months of review per subsystem, assumption), the drivers live in the Armbian sophgo-sg200x patch set and need a rebase per kernel release (small, because they use only stable DRM/V4L2 APIs). Residual maintenance owners: the libcamera pipeline handler/IPA and tuning files (libcamera moves fast; pipeline handlers need periodic updates), new sensor drivers, and any out-of-tree pieces maintainers reject (e.g. a vendor-specific params format if v4l2-isp.h framing is not accepted - then WS6 stays out-of-tree with ongoing churn). Hardware-knowledge risk: with no TRM for the ISP and vendor focus staying on linux_5.10 (ecosystem Q3), bug fixes for undocumented ISP behaviour depend on the porting team's own notes - keep the WS2/WS6 register maps as living documentation. Compared with Strategy A (lift-and-shift), B trades a 2-3x higher upfront cost for near-zero API-chase maintenance and community co-maintenance (BadgeOS/Armbian users as testers).
where_this_strategy_is_weak: Honest comparison: (1) Time-to-any-camera is the worst of the three. A lift-and-shift (Strategy A: infrastructure 8-17 + cif 2-4 + vi 6-10 + vpss 3-6 + vo/fb 3-12 per vendor-deps/cif-snsr/vi-isp/vpss/vo-mipitx-fb port_options A) gets the full vendor camera with vendor 3A, HDR, online VPSS and codec on 7.x in roughly 20-45 engineer-weeks, whereas B needs 60-120 to reach an auto-exposed camera and never reaches vendor picture quality or hardware codec. (2) Picture quality: B's 3A/tuning is written from scratch against undocumented statistics; A and the hybrid (Strategy C: A first, then wrap V4L2 nodes around vendor structs) keep the vendor-tuned ISP. (3) Estimate spread is largest for B (ISP 35-65 weeks kernel+IPA) because the ISP is not in the TRM; A's unknowns are bounded API mechanics. (4) Licensing: B's ISP/VPSS drivers are derivative of osdrv headers with unclear licence text, a problem A sidesteps by shipping the vendor modules as-is under their MODULE_LICENSE("GPL"). (5) Feature loss: no cvi_mpi, no codec, no sub-LVDS/HiSPi/BT-demux, no I80, no FreeRTOS fast boot, no vendor sensors until new drivers are written. (6) Skills: requires DRM + V4L2 + libcamera/3A specialists concurrently; A needs one generalist kernel engineer. (7) Calendar dependency on upstream reviewers that the team does not control. Where B is clearly stronger: display (TRM-documented, template available, 8-14 weeks, external testers, upstreamable, /dev/fb0 for free), long-term maintenance, security (no physical addresses/kernel pointers in uAPI, no /dev/mem), and use of standard userspace (Weston, GStreamer, libcamera). A sensible decision is therefore not B-or-A globally but B for display immediately, B for CSI-RX + raw capture, and a deferred, gated decision (G3) on the ISP/3A stage - possibly running Strategy A's vendor camera stack on the same 7.x kernel in the meantime as the fallback for products that need vendor image quality or codec.
