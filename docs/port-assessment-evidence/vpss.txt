Scaler (IMG_IN + SC + ODMA) -> V4L2: in offline MEM->MEM mode each SC instance is a classic 1-in/1-out m2m engine (crop, scale, mirror/flip, CSC, format conversion) and maps directly to the v4l2_m2m + vb2_dma_contig pattern of rockchip rga (rga.c:88-123, 832; 3,153 LOC), sun8i-rotate (1,347 LOC), meson-ge2d (1,055 LOC). Fit is PARTIAL: (a) IMG_V is one read DMA shared by SC_V1..V3 (cvi_vip_img.c:281-282; sc_bounding CVI_VIP_IMG_2_SC_V) so the HW is 1-in/3-out — V4L2 m2m is strictly 1:1, so either run one job per output (re-reading the source, losing the bandwidth advantage) or expose a media-controller device with one output and multiple capture nodes (non-m2m); (b) per-SC GOP overlay, privacy mask, border, cover and slice-buffer-to-encoder handshake (scaler.c:2302,2944,1812,2918,1960) have no V4L2 m2m equivalent and would be dropped or custom controls; (c) the online ISP->VPSS mode (SCL_INPUT_ISP cvi_vip_img.c:56-59, VPSS_CB_VI_ONLINE_TRIGGER vpss_core.c:1093-1104 triggered from vi.c:2962) makes the scalers part of the capture pipeline, which belongs in a V4L2 subdev/media-controller ISP driver (rkisp1 resizer+capture model), not in an m2m driver — so the camera use-case depends on a VI/ISP V4L2 driver that does not exist yet.
