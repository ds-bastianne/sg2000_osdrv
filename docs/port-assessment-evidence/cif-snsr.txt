userspace_contract: Today the kernel CIF driver is a thin register programmer; all camera-specific knowledge lives in the CVITEK middleware (libsns_<sensor>.so + libisp/libsys; not in this repo, so the following is inferred from the uAPI). (1) Receiver configuration is dictated by userspace per sensor mode via CVI_MIPI_SET_DEV_ATTR with struct combo_dev_attr_s (cif_uapi.h:272-283): input mode, MAC clock, MCLK frequency, and for MIPI struct mipi_dev_attr_s (cif_uapi.h:159-167) with raw_data_type, lane_id[5] (logical CLK/D0-D3 -> physical lane 0-5, -1 unused), pn_swap[5], wdr_mode (NONE/VC/DT/DOL/MANUAL), data_type[2] for DT-HDR, dphy.enable + dphy.hs_settle, demux vc_mapping[4], img_size, wdr_manu (manual HDR line geometry). So lane mapping, polarity, D-PHY hs_settle and HDR mode are all programmed by the userspace sensor driver, not derived in-kernel (verified: _cif_set_attr_mipi cif.c:464-640 only validates and applies). (2) Sensor power/clock sequencing is also driven from userspace: CVI_MIPI_RESET_SENSOR/UNRESET_SENSOR toggle the snsr-reset GPIO, CVI_MIPI_ENABLE/DISABLE_SENSOR_CLOCK and SET_SENSOR_CLOCK set MCLK from a 5-entry table (cif.c:2124-2146, 2514-2619). (3) Initial sensor register init over I2C: the kernel offers no init path (snsr_i2c has no read op and only runtime write/burst, snsr_i2c.c:347-366), so the sensor mode tables are most likely written by the middleware directly through /dev/i2c-N - likely, unverified (middleware not available). (4) Runtime 3A: the userspace ISP computes exposure/gain register groups and hands them to the kernel vi driver via VI_IOCTL_SET_SNR_CFG_NODE as struct snsr_cfg_node_s (vi_snsr.h:117-156: up to ISP_MAX_SNS_REGS=32 struct isp_i2c_data with i2c_dev, dev_addr, reg_addr/addr_bytes, data/data_bytes, dly_frm_num, drop_frame, vblank_update, plus a 'magic_num' target frame number); vi queues them (vi.c:5160-5195 -> _isp_snr_cfg_enq) and at frame-end/vblank of frame == magic_num fires them through snsr_i2c (vi.c:1815-1952). The burst mechanism exists so that a whole register group lands inside one vertical blanking: snsr_i2c_burst_queue collects up to 32 messages per adapter, each flagged I2C_M_WRSTOP (snsr_i2c.c:92-143, snsr_i2c.h:9), and snsr_i2c_burst_fire sends them in a single i2c_transfer (snsr_i2c.c:290-345), measuring the duration; vi selects burst vs single writes with module_param burst_i2c_en (vi.h:1463-1464; vi.c:1828). It uses a dummy i2c_client "sensor_i2c" at 0x3d (0x7b>>1) instantiated on every adapter 0..4 only to reach the adapter; the real slave address comes from isp_i2c_data.dev_addr (snsr_i2c.c:26-28, 65-67, 390-399). Binary compatibility: the CVITEK middleware links against this exact ioctl ABI ('m' magic, struct layouts with native enums, cif_uapi.h) and against the vi/sys/vb ABIs; any move to V4L2 breaks the proprietary middleware completely, and because the ISP 3A/tuning is closed-source userspace, a V4L2 port also needs a replacement 3A (libcamera IPA or vendor-provided) - the CIF/snsr_i2c part itself carries no algorithms. In the mainline model: sensor drivers in drivers/media/i2c own init tables, reset-gpios, clocks (CLK_CAM0/1) and expose exposure/gain as V4L2 controls; lane mapping/polarity come from the DT endpoint (data-lanes, clock-lanes, lane-polarities); hs_settle is derived from link-frequency via phy_mipi_dphy_get_default_config (include/linux/phy/phy-mipi-dphy.h:278); frame-synchronous control application is done by userspace (libcamera DelayedControls) - so snsr_i2c and the sensor-related CIF ioctls become unnecessary.
